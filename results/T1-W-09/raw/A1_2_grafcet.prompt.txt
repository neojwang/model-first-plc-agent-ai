Control task:
# Task T1 - Factory I/O Scene 2, From A to B (Set and Reset)

Plant: a conveyor transports a box from sensor A to sensor B (Factory I/O scene "From A to B (Set and Reset)").

I/O (OpenPLC Runtime with Factory I/O attached as a Modbus TCP slave device; map the scene tags to these addresses in the Factory I/O driver):
- Inputs: SensorA AT %IX100.0 : BOOL (TRUE while a box is detected at sensor A); SensorB AT %IX100.1 : BOOL (TRUE while a box is detected at sensor B).
- Output: Conveyor AT %QX100.0 : BOOL (TRUE runs the conveyor).

Requirements:
1. When a box is detected at sensor A, start the conveyor.
2. When the box reaches sensor B, stop the conveyor so that the box stays at sensor B.
3. Use a bistable function block of IEC 61131-3 (SR or RS) for the conveyor command.

Identifier vocabulary for receptivities and outputs (use exactly these names):
- inputs: sensor_a, sensor_b
- output: conveyor

IDEF0 model:
## IDEF0 model

### Modeling decisions

- Use an IEC 61131-3 **RS bistable function block** to retain the conveyor command after the box leaves sensor A.
- Use **reset dominance**: if `sensor_a` and `sensor_b` are both TRUE, stop the conveyor. This resolves a case not explicitly prioritized in the requirements.
- Assume an initial conveyor command of FALSE.
- Treat sensor detection as **level-sensitive**, not edge-sensitive. No code is specified here.

All function names below are verb phrases. Arrow names are noun phrases; the required identifiers `sensor_a`, `sensor_b`, and `conveyor` are preserved exactly.

### Child-diagram arrow connections

These connections define the A0 decomposition and balance its external interfaces.

| Arrow | Source | Destination | Meaning |
|---|---|---|---|
| `sensor_a` | A0 input boundary | A1 input | Box-presence indication at sensor A |
| `sensor_b` | A0 input boundary | A2 input | Box-presence indication at sensor B |
| Start request | A1 output | A3 input | Set request, TRUE while `sensor_a` is TRUE |
| Stop request | A2 output | A3 input | Reset request, TRUE while `sensor_b` is TRUE |
| Retained conveyor command | A3 output | A4 input | Stored run/stop command |
| `conveyor` | A4 output | A0 output boundary | Conveyor actuator command |

The A0 control arrows branch to the child functions listed in the ICOM table. Its mechanism arrows likewise support the indicated children.

### Control-arrow definitions

| Control arrow | Definition |
|---|---|
| Start-on-A requirement | Detection at sensor A requests conveyor operation. |
| Stop-at-B requirement | Detection at sensor B requests conveyor stoppage so the box remains at B. |
| Reset-dominance rule | A stop request overrides a simultaneous start request. |
| Initial-off policy | The retained conveyor command initially equals FALSE. |
| IEC 61131-3 bistable requirement | Conveyor-command retention uses an IEC 61131-3 SR or RS block; this model selects RS. |
| I/O address mapping | `sensor_a` → `%IX100.0`; `sensor_b` → `%IX100.1`; `conveyor` → `%QX100.0`. Factory I/O scene tags use the corresponding Modbus driver mapping. |

### Behavioral check for A3

| Start request | Stop request | Retained conveyor command |
|---|---|---|
| FALSE | FALSE | Previous command |
| TRUE | FALSE | TRUE |
| FALSE | TRUE | FALSE |
| TRUE | TRUE | FALSE — reset dominant |

Thus, detection at A starts the conveyor, the retained command keeps it running between sensors, and detection at B stops it. With neither sensor active afterward, the stopped state remains retained until another start request occurs.

GRAFCET JSON schema (the tuple of Equation (1) of the paper):

{
  "graphs": [ {"name": "G1", "steps": ["x0", "x1"], "initial": ["x0"]} ],
  "transitions": [ {"id": "t1", "from": ["x0"], "to": ["x1"], "guard": "start"} ],
  "outputs": { "fill_valve": "x1" },
  "forcing": [ {"by": "x11", "graph": "G1", "situation": ["x0"]} ],
  "owned": { "timer_done": {"step": "x1", "neutral": false, "preset": "TimerDuration"} }
}

Rules:
1. Step names start with the letter x followed by letters or digits (x0, x1, x21, xE1). The main graph is named G1, and x0 is its initial step.
2. A transition lists its upstream steps ("from"), its downstream steps ("to"), and its receptivity ("guard"). Guards use only the input identifiers of the task card, step names, the operators ! (not), & (and), | (or), parentheses, TRUE and FALSE; the level region of task T4 is tested as r = LOW, r = MID or r = HIGH.
3. "outputs" gives, for every output identifier of the task card, a Boolean expression over step names that is TRUE while the output is on.
4. "forcing" is optional: a separate graph (for example G0 for stop handling) may contain a step whose forcing order holds the graph named in "graph" in the listed situation.
5. "owned" lists every timer or hold condition used in a guard (timer_done, ton_q, tof_q, settled) with the step whose activity it measures, the value it has at the instant that step becomes active ("neutral"), and its preset, written as the parameter name of the task card ("preset"). Conditions that measure the duration of a step are FALSE at that instant; the off-delay output tof_q is measured by the pause step and is TRUE at that instant.
6. Output only the JSON object, without comments or explanations.
