Control task:
# Task T1 - Factory I/O Scene 2, From A to B (Set and Reset)

Plant: a conveyor transports a box from sensor A to sensor B (Factory I/O scene "From A to B (Set and Reset)").

I/O (OpenPLC Runtime with Factory I/O attached as a Modbus TCP slave device; map the scene tags to these addresses in the Factory I/O driver):
- Inputs: SensorA AT %IX100.0 : BOOL (TRUE while a box is detected at sensor A); SensorB AT %IX100.1 : BOOL (TRUE while a box is detected at sensor B).
- Output: Conveyor AT %QX100.0 : BOOL (TRUE runs the conveyor).

Requirements:
1. When a box is detected at sensor A, start the conveyor.
2. When the box reaches sensor B, stop the conveyor so that the box stays at sensor B.
3. Use a bistable function block of IEC 61131-3 (SR or RS) for the conveyor command.

Identifier vocabulary for receptivities and outputs (use exactly these names):
- inputs: sensor_a, sensor_b
- output: conveyor

IDEF0 model:
## IDEF0 model

### Modeling decisions

- **Scope:** Model the PLC control function, not the physical movement of the box. The conveyor and box are the controlled plant.
- **Bistable selection:** Use an IEC 61131-3 **RS bistable**, with reset dominance. Thus, if `sensor_a` and `sensor_b` are both TRUE, `conveyor` is FALSE. This resolves the unspecified simultaneous-detection case in favor of stopping at B.
- **Retention:** When both sensors are FALSE, the bistable retains its previous state. This keeps the conveyor running while the box travels between sensors.
- **Initialization assumption:** The retained command is initially FALSE. This is an assumption to confirm before implementation; restart and retentive-memory behavior are not specified by the task.

All function names below are verb phrases. Arrow names are noun phrases; the required signal identifiers are preserved exactly.

## A0 context function

**A0 — Control box transport from A to B**

| Node | Function | Inputs | Controls | Outputs | Mechanisms |
|---|---|---|---|---|---|
| A0 | Control box transport from A to B | `sensor_a`; `sensor_b` | Start-on-A requirement; Stop-at-B requirement; IEC 61131-3 bistable requirement; Reset-priority policy; Initial-off assumption; I/O address mapping | `conveyor` | OpenPLC Runtime; Modbus TCP interface; Factory I/O scene interface |

The A0 boundary receives the two detection signals and produces the conveyor command. Control requirements and configuration constrain that transformation; runtime and communication facilities enable it.

## A0 decomposition

**Functional flow:**

`A1 — Acquire sensor states` → `A2 — Maintain conveyor command` → `A3 — Publish conveyor command`

| Node | Function | Inputs | Controls | Outputs | Mechanisms |
|---|---|---|---|---|---|
| A1 | Acquire sensor states | `sensor_a`; `sensor_b` | Input address mapping; Cyclic input-sampling convention | `sensor_a`; `sensor_b` | OpenPLC input process image; Modbus TCP interface; Factory I/O sensor interface |
| A2 | Maintain conveyor command | `sensor_a`; `sensor_b` | Start-on-A requirement; Stop-at-B requirement; State-hold requirement; IEC 61131-3 bistable requirement; Reset-priority policy; Initial-off assumption | `conveyor` | IEC 61131-3 RS bistable instance; Bistable state memory; OpenPLC cyclic execution |
| A3 | Publish conveyor command | `conveyor` | Output address mapping; Cyclic output-update convention | `conveyor` | OpenPLC output process image; Modbus TCP interface; Factory I/O conveyor interface |

**Signal representation:** At A1, the identically named input and output arrows represent external sensor values and their sampled PLC values, respectively. At A3, they represent the internal command and its published actuator value. These are representation changes, not additional signal identifiers.

### Behavioral constraint on A2

GRAFCET JSON schema (the tuple of Equation (1) of the paper):

{
  "graphs": [ {"name": "G1", "steps": ["x0", "x1"], "initial": ["x0"]} ],
  "transitions": [ {"id": "t1", "from": ["x0"], "to": ["x1"], "guard": "start"} ],
  "outputs": { "fill_valve": "x1" },
  "forcing": [ {"by": "x11", "graph": "G1", "situation": ["x0"]} ],
  "owned": { "timer_done": {"step": "x1", "neutral": false, "preset": "TimerDuration"} }
}

Rules:
1. Step names start with the letter x followed by letters or digits (x0, x1, x21, xE1). The main graph is named G1, and x0 is its initial step.
2. A transition lists its upstream steps ("from"), its downstream steps ("to"), and its receptivity ("guard"). Guards use only the input identifiers of the task card, step names, the operators ! (not), & (and), | (or), parentheses, TRUE and FALSE; the level region of task T4 is tested as r = LOW, r = MID or r = HIGH.
3. "outputs" gives, for every output identifier of the task card, a Boolean expression over step names that is TRUE while the output is on.
4. "forcing" is optional: a separate graph (for example G0 for stop handling) may contain a step whose forcing order holds the graph named in "graph" in the listed situation.
5. "owned" lists every timer or hold condition used in a guard (timer_done, ton_q, tof_q, settled) with the step whose activity it measures, the value it has at the instant that step becomes active ("neutral"), and its preset, written as the parameter name of the task card ("preset"). Conditions that measure the duration of a step are FALSE at that instant; the off-delay output tof_q is measured by the pause step and is TRUE at that instant.
6. Output only the JSON object, without comments or explanations.
