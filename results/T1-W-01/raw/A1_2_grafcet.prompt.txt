Control task:
# Task T1 - Factory I/O Scene 2, From A to B (Set and Reset)

Plant: a conveyor transports a box from sensor A to sensor B (Factory I/O scene "From A to B (Set and Reset)").

I/O (OpenPLC Runtime with Factory I/O attached as a Modbus TCP slave device; map the scene tags to these addresses in the Factory I/O driver):
- Inputs: SensorA AT %IX100.0 : BOOL (TRUE while a box is detected at sensor A); SensorB AT %IX100.1 : BOOL (TRUE while a box is detected at sensor B).
- Output: Conveyor AT %QX100.0 : BOOL (TRUE runs the conveyor).

Requirements:
1. When a box is detected at sensor A, start the conveyor.
2. When the box reaches sensor B, stop the conveyor so that the box stays at sensor B.
3. Use a bistable function block of IEC 61131-3 (SR or RS) for the conveyor command.

Identifier vocabulary for receptivities and outputs (use exactly these names):
- inputs: sensor_a, sensor_b
- output: conveyor

IDEF0 model:
## IDEF0 model

### Modeling decisions

- Use an IEC 61131-3 **RS bistable function block**: `sensor_a` sets the command and `sensor_b` resets it.
- **Reset dominance is a design choice:** if both sensors are TRUE, the conveyor stops. This gives priority to retaining the box at sensor B.
- With neither sensor TRUE, the bistable retains its previous state.
- **Initialization assumption:** the conveyor command is FALSE at startup. Restart retention is not specified by the task.

### A0 context function and decomposition

All function names are verb phrases; all arrow names are noun phrases. The identifiers `sensor_a`, `sensor_b`, and `conveyor` are used exactly as requested.

| Node | Function | Inputs | Controls | Outputs | Mechanisms |
|---|---|---|---|---|---|
| **A0** | **Transport a box from A to B** | `sensor_a`; `sensor_b` | Start-on-A requirement; stop-at-B requirement; IEC 61131-3 bistable requirement; reset-priority policy; startup initialization policy; I/O address map | `conveyor` | OpenPLC Runtime; IEC 61131-3 RS function block; PLC state memory; Modbus TCP connection; Factory I/O conveyor plant |
| **A1** | **Maintain the conveyor command** | `sensor_a`; `sensor_b` | Start-on-A requirement; stop-at-B requirement; IEC 61131-3 bistable requirement; reset-priority policy; startup initialization policy | Latched conveyor command | IEC 61131-3 RS function block; PLC state memory; OpenPLC cyclic execution |
| **A2** | **Apply the conveyor command** | Latched conveyor command | I/O address map; output polarity convention | `conveyor` | OpenPLC output image; Modbus TCP connection; Factory I/O conveyor actuator |

### Arrow connections

- **A0 input → A1 input:** `sensor_a`
- **A0 input → A1 input:** `sensor_b`
- **A1 output → A2 input:** Latched conveyor command
- **A2 output → A0 output:** `conveyor`

The bistable’s retained state is internal to **A1**, supported by PLC state memory. It is not an additional external input.

### Control-arrow definitions

| Control arrow | Meaning |
|---|---|
| Start-on-A requirement | A TRUE `sensor_a` sets the conveyor command unless reset is active. |
| Stop-at-B requirement | A TRUE `sensor_b` resets the conveyor command. |
| IEC 61131-3 bistable requirement | The command is maintained by an SR or RS function block; this model selects RS. |
| Reset-priority policy | Simultaneous TRUE sensor signals produce an OFF command. |
| Startup initialization policy | The initial latched command is FALSE. |
| I/O address map | `sensor_a` → `%IX100.0`; `sensor_b` → `%IX100.1`; `conveyor` → `%QX100.0`. |
| Output polarity convention | TRUE runs the conveyor; FALSE stops it. |

This model treats stopping the conveyor as sufficient to leave the box at sensor B, consistent with the stated Factory I/O task.

GRAFCET JSON schema (the tuple of Equation (1) of the paper):

{
  "graphs": [ {"name": "G1", "steps": ["x0", "x1"], "initial": ["x0"]} ],
  "transitions": [ {"id": "t1", "from": ["x0"], "to": ["x1"], "guard": "start"} ],
  "outputs": { "fill_valve": "x1" },
  "forcing": [ {"by": "x11", "graph": "G1", "situation": ["x0"]} ],
  "owned": { "timer_done": {"step": "x1", "neutral": false, "preset": "TimerDuration"} }
}

Rules:
1. Step names start with the letter x followed by letters or digits (x0, x1, x21, xE1). The main graph is named G1, and x0 is its initial step.
2. A transition lists its upstream steps ("from"), its downstream steps ("to"), and its receptivity ("guard"). Guards use only the input identifiers of the task card, step names, the operators ! (not), & (and), | (or), parentheses, TRUE and FALSE; the level region of task T4 is tested as r = LOW, r = MID or r = HIGH.
3. "outputs" gives, for every output identifier of the task card, a Boolean expression over step names that is TRUE while the output is on.
4. "forcing" is optional: a separate graph (for example G0 for stop handling) may contain a step whose forcing order holds the graph named in "graph" in the listed situation.
5. "owned" lists every timer or hold condition used in a guard (timer_done, ton_q, tof_q, settled) with the step whose activity it measures, the value it has at the instant that step becomes active ("neutral"), and its preset, written as the parameter name of the task card ("preset"). Conditions that measure the duration of a step are FALSE at that instant; the off-delay output tof_q is measured by the pause step and is TRUE at that instant.
6. Output only the JSON object, without comments or explanations.
