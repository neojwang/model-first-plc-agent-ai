Control task:
# Task T3 - Factory I/O Scene 3, Filling Tank (Timers), TON and TOF timers

Plant: as in T2 (digital tank configuration, customized with level switches LSH at 2.4 m and LSHH at 2.7 m).

I/O (OpenPLC Runtime with Factory I/O attached as a Modbus TCP slave device; map the scene tags to these addresses in the Factory I/O driver):
- Inputs: StartCommand AT %IX100.0 : BOOL; StopCommand AT %IX100.1 : BOOL; LSH AT %IX100.2 : BOOL; LSHH AT %IX100.3 : BOOL.
- Outputs: FillValve AT %QX100.0 : BOOL; DischargeValve AT %QX100.1 : BOOL (keep FALSE in this task).
- Parameters: TON_Duration : TIME; TOF_Duration : TIME.

Requirements:
1. Step 0 is the initial step; it drives no output.
2. On StartCommand, fill: open the fill valve in a filling step. An on-delay timer TON with IN := activity of the filling step limits each filling phase to TON_Duration.
3. When TON has elapsed and LSH does not detect the liquid, close the fill valve (pause step). An off-delay timer TOF with IN := activity of the filling step keeps its output TRUE for TOF_Duration after the filling step is left; when the TOF output is FALSE, resume filling.
4. When LSH detects the liquid, end filling with the fill valve closed and return to step 0. LSHH must never be reached.
5. Whenever StopCommand is TRUE, return to step 0 with all outputs FALSE.

Identifier vocabulary for receptivities and outputs (use exactly these names):
- inputs: start (the event of pressing StartCommand: TRUE only in the scan in which the button is pressed), stop, LSH, LSHH, ton_q (output Q of TON), tof_q (output Q of TOF)
- outputs: fill_valve, discharge_valve

## A0 context and decomposition

**A0 — Control timed tank filling**

**Purpose:** Fill the tank in timed phases separated by timed pauses, terminate filling at LSH, and return to the initial state on StopCommand.

**Boundary:** The model includes input conditioning, supervisory decisions, step sequencing, timer evaluation, and output commanding. The simulated tank, valves, and level switches form the external plant.

### Modeling conventions

- **Inputs** are information transformed by a function.
- **Controls** are rules, constraints, or settings governing a function.
- **Outputs** are the results of a function.
- **Mechanisms** are the resources performing a function.
- All function names below are verb phrases. Arrow names are noun phrases.
- **Step 0**, **Filling step**, and **Pause step** are mutually exclusive states.
- The specified identifiers `start`, `stop`, `LSH`, `LSHH`, `ton_q`, `tof_q`, `fill_valve`, and `discharge_valve` are preserved.

## Governing controls

### Supervisory rules

A2 produces:

- **Filling permission:** present only when `stop`, `LSH`, and `LSHH` are all FALSE.
- **Step-0 reset demand:** present whenever `stop`, `LSH`, or `LSHH` is TRUE.

Thus, a level or stop condition prevents even a momentary start of filling. Reset demand takes priority over every normal transition.

**LSHH interpretation:** The requirement that LSHH must never be reached is modeled as a safety constraint, with an additional protective inhibit if `LSHH` is detected. Normal termination remains at LSH. No alarm latch or manual fault-reset behavior is assumed.

### State-transition rules

| Current state | Condition | Next state |
|---|---|---|
| Any state | `stop` is TRUE | Step 0 |
| Any state | `LSH` or `LSHH` is TRUE | Step 0 |
| Step 0 | `start` is TRUE and filling permission is present | Filling step |
| Filling step | `ton_q` is TRUE and filling permission is present | Pause step |
| Pause step | `tof_q` is FALSE and filling permission is present | Filling step |
| Any state | No applicable transition condition | Current state |

The rows are evaluated with the stated reset priority. A held StartCommand does not repeatedly start the process: only its rising-edge event produces `start`.

### Timer rules

| Timer | Input activity | Time setting | Required behavior |
|---|---|---|---|
| TON | Filling-step activity | TON_Duration | `ton_q` becomes TRUE after continuous filling-step activity for TON_Duration. Leaving the filling step resets the TON. |
| TOF | Filling-step activity | TOF_Duration | `tof_q` is TRUE during filling and remains TRUE for TOF_Duration after the filling step is left. Its subsequent FALSE state permits resumption from the Pause step. |

Both timers have initialized, non-retentive state. The TOF may remain TRUE temporarily after a stop or level-completion event, but that status cannot open the valve or leave Step 0 without a new valid `start`.

### Valve-command rules

| Operating condition | `fill_valve` | `discharge_valve` |
|---|---:|---:|
| Step 0 | FALSE | FALSE |
| Filling step with filling permission | TRUE | FALSE |
| Pause step | FALSE | FALSE |
| Step-0 reset demand | FALSE | FALSE |

**Physical safety qualification:** Preventing the actual liquid level from reaching 2.7 m also requires adequate margin between LSH and LSHH for input sampling, communications, valve closure, and residual inflow. The logical model alone cannot guarantee that physical margin; it must be validated against the plant dynamics.

{
  "graphs": [ {"name": "G1", "steps": ["x0", "x1"], "initial": ["x0"]} ],
  "transitions": [ {"id": "t1", "from": ["x0"], "to": ["x1"], "guard": "start"} ],
  "outputs": { "fill_valve": "x1" },
  "forcing": [ {"by": "x11", "graph": "G1", "situation": ["x0"]} ],
  "owned": { "timer_done": {"step": "x1", "neutral": false, "preset": "TimerDuration"} }
}

Rules:
1. Step names start with the letter x followed by letters or digits (x0, x1, x21, xE1). The main graph is named G1, and x0 is its initial step.
2. A transition lists its upstream steps ("from"), its downstream steps ("to"), and its receptivity ("guard"). Guards use only the input identifiers of the task card, step names, the operators ! (not), & (and), | (or), parentheses, TRUE and FALSE; the level region of task T4 is tested as r = LOW, r = MID or r = HIGH.
3. "outputs" gives, for every output identifier of the task card, a Boolean expression over step names that is TRUE while the output is on.
4. "forcing" is optional: a separate graph (for example G0 for stop handling) may contain a step whose forcing order holds the graph named in "graph" in the listed situation.
5. "owned" lists every timer or hold condition used in a guard (timer_done, ton_q, tof_q, settled) with the step whose activity it measures, the value it has at the instant that step becomes active ("neutral"), and its preset, written as the parameter name of the task card ("preset"). Conditions that measure the duration of a step are FALSE at that instant; the off-delay output tof_q is measured by the pause step and is TRUE at that instant.
6. Output only the JSON object, without comments or explanations.
