Control task:
# Task T1 - Factory I/O Scene 2, From A to B (Set and Reset)

Plant: a conveyor transports a box from sensor A to sensor B (Factory I/O scene "From A to B (Set and Reset)").

I/O (OpenPLC Runtime with Factory I/O attached as a Modbus TCP slave device; map the scene tags to these addresses in the Factory I/O driver):
- Inputs: SensorA AT %IX100.0 : BOOL (TRUE while a box is detected at sensor A); SensorB AT %IX100.1 : BOOL (TRUE while a box is detected at sensor B).
- Output: Conveyor AT %QX100.0 : BOOL (TRUE runs the conveyor).

Requirements:
1. When a box is detected at sensor A, start the conveyor.
2. When the box reaches sensor B, stop the conveyor so that the box stays at sensor B.
3. Use a bistable function block of IEC 61131-3 (SR or RS) for the conveyor command.

Identifier vocabulary for receptivities and outputs (use exactly these names):
- inputs: sensor_a, sensor_b
- output: conveyor

IDEF0 model:
## Scope and modeling decisions

The model covers the **PLC control function**. Box movement and sensor actuation belong to the external Factory I/O plant.

- **Inputs:** `sensor_a`, `sensor_b`
- **Output:** `conveyor`
- **Bistable selection:** IEC 61131-3 **RS**, with reset dominance. If both sensors are TRUE, the conveyor stops, giving the sensor B stopping requirement priority.
- Arrows represent Boolean information unless identified as rules, configuration, or execution resources.

## IDEF0 ICOM model

The **A0 context function** is decomposed into **A1–A3**. Every function name is a verb phrase; arrow names are noun phrases.

| Node | Function | Inputs | Controls | Outputs | Mechanisms |
|---|---|---|---|---|---|
| **A0** | **Control conveyor transport from A to B** | `sensor_a`; `sensor_b` | Start rule; Stop rule; State-retention rule; Reset-priority rule; I/O mapping configuration | `conveyor` | OpenPLC Runtime; IEC 61131-3 RS function block; Modbus TCP connection; Factory I/O slave interface |
| **A1** | **Generate the start request** | `sensor_a` | Start rule; I/O mapping configuration | Start request | OpenPLC Runtime; Modbus TCP connection; Factory I/O slave interface |
| **A2** | **Generate the stop request** | `sensor_b` | Stop rule; I/O mapping configuration | Stop request | OpenPLC Runtime; Modbus TCP connection; Factory I/O slave interface |
| **A3** | **Maintain and issue the conveyor command** | Start request; Stop request | State-retention rule; Reset-priority rule; I/O mapping configuration | `conveyor` | OpenPLC Runtime; IEC 61131-3 RS function block; Modbus TCP connection; Factory I/O slave interface |

## Arrow definitions

### Boundary and internal data arrows

| Arrow | Meaning | Source → Destination |
|---|---|---|
| `sensor_a` | TRUE while a box is detected at sensor A; mapped to `%IX100.0` | External plant → A0 boundary → A1 |
| `sensor_b` | TRUE while a box is detected at sensor B; mapped to `%IX100.1` | External plant → A0 boundary → A2 |
| Start request | Set demand equal to the current value of `sensor_a` | A1 → A3 |
| Stop request | Reset demand equal to the current value of `sensor_b` | A2 → A3 |
| `conveyor` | Retained conveyor command; TRUE runs the conveyor; mapped to `%QX100.0` | A3 → A0 boundary → External plant |

### Control arrows

| Arrow | Meaning |
|---|---|
| Start rule | Detection at sensor A requests conveyor operation. |
| Stop rule | Detection at sensor B requests conveyor stoppage. |
| State-retention rule | With neither request active, the bistable retains its previous command. |
| Reset-priority rule | An active stop request overrides an active start request. |
| I/O mapping configuration | Factory I/O driver mappings associate `sensor_a`, `sensor_b`, and `conveyor` with their specified OpenPLC addresses through the Modbus TCP slave interface. |

GRAFCET JSON schema (the tuple of Equation (1) of the paper):

{
  "graphs": [ {"name": "G1", "steps": ["x0", "x1"], "initial": ["x0"]} ],
  "transitions": [ {"id": "t1", "from": ["x0"], "to": ["x1"], "guard": "start"} ],
  "outputs": { "fill_valve": "x1" },
  "forcing": [ {"by": "x11", "graph": "G1", "situation": ["x0"]} ],
  "owned": { "timer_done": {"step": "x1", "neutral": false, "preset": "TimerDuration"} }
}

Rules:
1. Step names start with the letter x followed by letters or digits (x0, x1, x21, xE1). The main graph is named G1, and x0 is its initial step.
2. A transition lists its upstream steps ("from"), its downstream steps ("to"), and its receptivity ("guard"). Guards use only the input identifiers of the task card, step names, the operators ! (not), & (and), | (or), parentheses, TRUE and FALSE; the level region of task T4 is tested as r = LOW, r = MID or r = HIGH.
3. "outputs" gives, for every output identifier of the task card, a Boolean expression over step names that is TRUE while the output is on.
4. "forcing" is optional: a separate graph (for example G0 for stop handling) may contain a step whose forcing order holds the graph named in "graph" in the listed situation.
5. "owned" lists every timer or hold condition used in a guard (timer_done, ton_q, tof_q, settled) with the step whose activity it measures, the value it has at the instant that step becomes active ("neutral"), and its preset, written as the parameter name of the task card ("preset"). Conditions that measure the duration of a step are FALSE at that instant; the off-delay output tof_q is measured by the pause step and is TRUE at that instant.
6. Output only the JSON object, without comments or explanations.
