# GRAFCET virtual machine (GVM): one description, equivalent Python, C++, and ST programs

The GRAFCET tuple of the paper (Equation (1)), stored as JSON in the schema of `exec/prompts/templates/_schema.md`,
serves as the description language of a GRAFCET virtual machine (reference [14] of the paper). From one description,
`grafcet2gvm.py` generates three programs that execute one evolution of the GRAFCET to a stable situation per tick:
a Python module, a C++ header with a command-line driver, and an IEC 61131-3 Structured Text (ST) program for
OpenPLC. The evolution semantics are those of `nusmv/grafcet2smv.py`, that is, of the model that NuSMV checks:
simultaneous firing, forcing orders applied in the same micro-step, inputs not re-read during a transient run, events
valid in the first micro-step only, and conditions owned by a step at their neutral value until that step has been
active since the start of the evolution.

| File | Content |
|---|---|
| `grafcet2gvm.py` | Generator: JSON → `<name>_gvm.py`, `<name>_gvm.hpp`, `<name>_gvm_main.cpp`, `<name>_gvm.st`, and `<name>_gvm_io.json` (the located addresses of the ST program) |
| `e3_check.py` | Lockstep equivalence check (E3): the generated programs and the explicit-state model of `nusmv/grafcet2smv.py` run tick by tick on the same inputs; after every tick, the situation, the stability flag, and the outputs are compared |
| `generated/` | The programs generated from `nusmv/tank_reference.json`, the reference GRAFCET of the tank tasks (Fig. 6 and Tables 3–5 of the paper) |
| `e3_log.txt` | Result of `e3_check.py` with the ST program compiled by matiec at the pinned OpenPLC_v3 commit |
| `gvm_colab.ipynb` | Google Colab notebook: generate the Python and C++ programs, check them, and step them by hand (no PLC or FPGA needed) |

Coverage of `e3_check.py`: every input combination from every reachable stable situation of the model, each reached
from the initial situation by a shortest input path, plus random input sequences (seed 20261113). E3 counts the ticks
in which a program differs from the model; the programs are equivalent to the model on the tested inputs when E3 = 0.
Negative controls (an event read in every micro-step, the forcing order dropped, one receptivity negated) must give
E3 > 0, so that a check that cannot fail is not mistaken for a pass.

Usage:

```
python3 gvm/grafcet2gvm.py nusmv/tank_reference.json --out gvm/generated
python3 gvm/e3_check.py nusmv/tank_reference.json --openplc OPENPLC_V3_DIR --out gvm/generated --log gvm/e3_log.txt
python3 gvm/e3_check.py nusmv/tank_reference.json --out /tmp/gvm      # Python and C++ only, for example in Colab
```

Inputs are given in the order of "inputs" in the JSON: Boolean inputs as 0 or 1, enumerated inputs as the index of
their value (for the tank reference: mode timer 0, tontof 1, pid 2; r LOW 0, MID 1, HIGH 2). As in the model check,
the timer, hold, and logging conditions are inputs of the GRAFCET. The programs in `generated/` are therefore
executable versions of the model; they are neither the hand-written reference programs of `pilot/` nor the programs
generated by the LLM, which are added to `results/` after the experiment.
